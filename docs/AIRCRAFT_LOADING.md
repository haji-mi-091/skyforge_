# 飞机启动预加载与模型缓存

2026-10-22，用户批准合并飞机加载、缓存和材质预热；概念登记在 `REPO_CONTRACT.md` §2.3、§2.4。

## 启动顺序

`Game.init()` 先按 `AIRCRAFT_TYPES` 创建全部现役机型的隐藏预热实例，等待各自 `ready`，再创建世界和初始机库展示机。原 MiG-29 敌机池预热并入 `_prewarmAircraftMaterials()`：在实际场景、灯光和渲染器下预热外观、座舱、已登记涂装、尾焰、炮口火光及原敌机池的特效。全部完成、初始展示机装配并同步姿态后，才隐藏加载页并显示主菜单。失败沿现有启动错误页报告机型名称，不进入菜单。

预热实例保存在 `Game.aircraftWarmJets`，离开场景后仍保留至页面关闭，使已编译材质的程序引用保持有效。它们不作为玩家／机库实例使用，也不参与仿真；敌机仍使用已有敌机池。

## 模型缓存和所有权

唯一入口为 `src/visual/modelCache.js` 的 `loadCachedModel(url)`。按绝对 URL 合并正在进行的 GLTF 加载，并在当前页面中保留解析模板。失败的 Promise 从缓存移除，允许后续重试。F-16、歼-16、歼-10C 的现有加载入口都调用它；程序化 MiG-29 不需要 GLB 模板。

每次调用返回新的对象树，并按实例复制几何、材质和贴图；同一实例内保留相同资源的共享关系，glTF 元数据由对象克隆复制。模板不交给调用方，不修改、不由单个飞机的 `dispose()` 释放。实例的铰链、涂装、挂载离架和销毁不会改写模板或其他实例。现有共享 VFX／蒙皮贴图仍按其原有生命周期处理。

缓存只在当前页面内有效，不新增磁盘缓存、Service Worker、localStorage、URL 参数或依赖。缓存和驻留预热实例增加内存，且从模板创建实例仍有装配成本；不保证任意构型、视角或图形设置都零卡顿。

## F-16 加载门控

配置 `visual.cadModel` 时，`JetModel.group` 从创建起隐藏，`sync()`／座舱切换在加载期间不能将它重新显示。`ready` 在 CAD 装配并重放最近一次同步状态后完成，才显示正确模型。程序化外形仍为现有座舱及接口提供内部对象，不能充当可见加载占位。

三种 Jet 统一提供 `airframe` 就绪根：F-16 为装配后的 CAD 根，MiG-29 为其程序化 `group`，其余机型沿用原字段。现有 `CombatSystem.launchMissile` 使用该字段与 `ready` 判断显示模型是否就绪，因此补齐 `ready` 时也必须补齐 `airframe`；不另增一套发射就绪规则。

`dispose()` 标记实例已释放并清空对象树；迟到的加载结果仅释放资源，不继续装配。加载失败向 `ready` 的等待者传播；游戏启动仍使用现有 `Game.start()` 的等待／报错路径。
